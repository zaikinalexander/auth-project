# Система авторизации и управления доступом

Веб-приложение с JWT-авторизацией, ролями и динамическими страницами:
администратор создаёт их без перезапуска и выдаёт доступ в любой комбинации.

## Стек

| Слой      | Технология                                          |
|-----------|-----------------------------------------------------|
| Бэкенд    | Spring Boot 3.5, Spring Security, JJWT, Java 21     |
| Фронтенд  | Vue 3, Pinia, Vue Router, Axios, Vite               |
| База      | PostgreSQL (Flyway-миграции)                        |
| Сессии    | Redis (refresh-токены)                              |
| Деплой    | nginx + systemd, Ubuntu 24.04                       |

## Возможности

- Вход по email и паролю (Argon2id-хеш пароля).
- Двухтокенная схема: access 15 минут (в памяти браузера),
  refresh 7 дней (HttpOnly Secure SameSite=Strict cookie, в Redis только SHA-256 хеш).
- Ротация refresh-токена; повторное использование старого токена
  отзывает всё семейство сессий устройства.
- Роли: ADMIN, USER.
- Страницы хранятся в базе и создаются администратором без перезапуска.
  Доступ выдаётся в любой комбинации, коды страниц динамические.
- Админка: пользователи (создание, удаление, роль, статус, набор страниц),
  страницы (создание, правка, удаление), активные сессии и их завершение,
  журнал аудита.
- Активные сессии: по каждой известны пользователь, IP, User-Agent, время
  создания и последней активности. Можно завершить одну сессию, все сессии
  пользователя или все свои кроме текущей.
- Личный кабинет любого вошедшего: профиль, свои страницы, свои сессии,
  смена пароля, после которой завершаются все сессии.
- Защита от перебора паролей: 5 неудач за 5 минут на связку IP+email.
- Проверка прав всегда на бэкенде, фронтенд лишь скрывает ссылки.
- Журнал аудита: входы и отказы с причиной, действия администратора,
  просмотр страниц и отказы в доступе. Секреты не пишутся, хранение 90 дней.

## Схема данных: страницы и сессии

### Страницы (PostgreSQL, миграция V3)

```
pages
  code        varchar(64)   PRIMARY KEY          -- ^[A-Z0-9_]{3,64}$, неизменяем
  title       varchar(200)  NOT NULL
  content     text
  created_at  timestamptz   NOT NULL DEFAULT now()

user_pages
  user_id     uuid          NOT NULL  REFERENCES users(id)   ON DELETE CASCADE
  page_code   varchar(64)   NOT NULL  REFERENCES pages(code) ON DELETE CASCADE
  PRIMARY KEY (user_id, page_code)
```

Код страницы служит первичным ключом, поэтому назначения в `user_pages`
ссылаются на `pages(code)`. Каскад при удалении страницы сам снимает право
у всех пользователей. До V3 таблица `pages` имела суррогатный ключ `id`,
а назначения хранили `page_id`; V3 переносит данные, а не пересоздаёт их.

Доступ проверяется на бэкенде: в JWT лежат права `PAGE_<КОД>`, а `AccessChecker`
сверяет код из пути с правами вызывающего. Роль ADMIN проходит всегда.
Список кодов нигде не захардкожен, поэтому новая страница начинает работать
сразу после выдачи права.

### Сессии (Redis)

Сессия — это семейство ротаций refresh-токена одного устройства.

```
rt:<sha256(refresh)>   -> {userId, family, expiresAt}      TTL = срок refresh
fam:<familyId>         -> SET хешей выданных токенов семейства TTL = срок refresh
used:<sha256(refresh)> -> familyId                          TTL = срок refresh
ses:<familyId>         -> {familyId, userId, userEmail,
                           createdAt, lastUsedAt, ip, userAgent}
usr:<userId>           -> SET familyId пользователя
ses:index              -> SET всех familyId                 (для админского списка)
at:<jti access-токена> -> familyId                          TTL = срок access
```

Самого refresh-токена в Redis нет — только SHA-256 хеш. `userAgent`
обрезается до 256 символов.

Связка `at:<jti>` нужна потому, что refresh-cookie имеет узкий
`Path=/api/auth` и браузер не отправляет её на `/api/me/sessions`. Чтобы
отличить текущую сессию от прочих в личном кабинете, access-токен при
выдаче одноразово связывается со своим семейством по уже существующему
в токене `jti`.
Схема токена при этом не меняется: `jti` был в нём и раньше.

Завершение сессии удаляет `rt:*` её семейства и саму запись `ses:*`.
Refresh-токен умирает немедленно, access-токен доживает до 15 минут — это свойство
stateless-схемы из ТЗ, а не ошибка. Подробности и обходной путь
(отключение учётной записи) описаны в `USER_GUIDE.md`.

## CSRF и почему он неприменим

Межсайтовая подделка запроса опирается на то, что браузер сам прикладывает
cookie к запросу на чужой сайт. Здесь атака не сходится по четырём
независимым причинам. Каждая проверена в `deploy/smoke-test.sh`, раздел
«CSRF: почему межсайтовая подделка запроса неприменима».

1. **Основной токен передаётся в заголовке `Authorization`, а не в cookie.**
   Access-токен живёт только в памяти вкладки (`authToken.current` в
   `frontend/src/api/http.js`) и подставляется перехватчиком Axios. Его
   значение знают лишь скрипты нашего origin: сторонний сайт не может ни
   прочитать токен, ни приложить его к своему запросу.

2. **Refresh-cookie помечен `SameSite=Strict`.**
   Браузер не прикладывает такой cookie ни к одному межсайтовому запросу —
   ни к «простому», ни к возникшему после перехода по ссылке. Запрос с
   `evil.example` придёт без cookie, и `/api/auth/refresh` ответит 401.
   `Path=/api/auth` дополнительно сужает область отправки, а `HttpOnly`
   закрывает чтение значения из JavaScript.

3. **API принимает только JSON, кросс-доменных разрешений нет.**
   Форма с `application/x-www-form-urlencoded` — единственный способ, которым
   чужой сайт может отправить POST без предзапроса, — получает
   `415 Unsupported Media Type`. На `OPTIONS`-предзапрос с
   `Origin: https://evil.example` сервер не возвращает ни
   `Access-Control-Allow-Origin`, ни `Access-Control-Allow-Credentials`,
   поэтому браузер заблокирует и запрос, и чтение ответа.

4. **Вход cookie не использует.**
   `POST /api/auth/login` принимает email и пароль в JSON-теле,
   аутентификации по cookie на этом маршруте нет. Значит ни принудительный
   вход (login CSRF), ни подделка действия уже залогиненного пользователя
   не имеют точки приложения.

Отсюда следует, что `csrf.disable()` в `SecurityConfig` — осознанное решение
для stateless-API, а не упущение. Оно безопасно ровно пока выполняются все
четыре пункта. Защиту CSRF придётся включить заново, если появится
аутентификация по cookie для маршрутов вне `/api/auth`, если API начнёт
отдавать `Access-Control-Allow-Origin`, или если будет принят
`Content-Type: application/x-www-form-urlencoded`. Проверки в smoke-тесте
ловят такую регрессию.

## Переменные окружения (бэкенд)

DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD,
REDIS_HOST, REDIS_PORT, REDIS_PASSWORD,
JWT_PRIVATE_KEY_PATH, JWT_PUBLIC_KEY_PATH,
ADMIN_EMAIL, ADMIN_INITIAL_PASSWORD (только для первого запуска),
AUDIT_RETENTION_DAYS (срок хранения журнала аудита в днях, по умолчанию 90).

В продакшене все секреты лежат в /etc/auth-backend/env (права 640),
вне репозитория и вне веб-папки.
